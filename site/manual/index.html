The skill

splat-site

/splat-site <video-or-scene> [fast(default)|balanced|high]

/splat-site clip.mp4                 a scene and a site in minutes
/splat-site clip.mp4 high            trains for 30-60 min, best quality, GPU only
/splat-site ./scene balanced         a scene folder that already exists

Invoked with no arguments

Print the usage block above and stop. Do not interview, do not ask which capture to use, do not start work. A bare invocation is someone checking the form of the command, and the useful answer is the form itself plus one line on what to include: the video or scene folder, the level if it is not fast, and where the photos are if there are any. Then wait.

A phone video becomes a Gaussian-splat capture, and the capture becomes a website the visitor scrolls through. Two halves, two different kinds of work: the first is a pipeline with known failure modes, the second is design. This skill runs the first and hands the second to scroll-craft with the 3D world already wired up as a device it can score.

What you produce: a scene folder (compressed capture tiers, camera poses, posters), a brief, a built site whose fixed world is the real capture, evidence that it renders at desktop and phone sizes and with motion reduced, and a plain account of what was not covered.

What has to be in place

  • The splatsite CLI (Node 22+). It ships inside this plugin at <plugin>/cli and the scripts here find it there automatically; it may also be on PATH, otherwise run node <cli>/bin/splatsite.mjs. The resolution order is $SPLATSITE_CLI, the plugin's own cli/, a splatsite on PATH, then a splatsite/cli above the cwd. Say which checkout you used.
  • Docker, for reconstruction only. A host GPU is detected and used automatically. Without one, only --quality fast is possible.
  • The scroll-craft skill — required, not optional. Every website this skill produces is built through scroll-craft: it owns the page's grammar, its feeling curve, its signature move, the fingerprint gate that stops builds repeating each other, and the taste floor. This skill owns the 3D and hands the page over. Never design the page yourself instead.
  • Source: <https://github.com/nateherkai/scroll-craft>, installed as the nateherk-design plugin (/plugin marketplace add nateherkai/scroll-craft, then install and enable it).
  • Invoke it by name: scroll-craft, or nateherk-design:scroll-craft under its plugin.
  • If the invocation fails with "unknown skill", the plugin is on disk but not registered in this session — plugin skills register at session start, so a mid-session install needs /reload-plugins. Then read its SKILL.md under ~/.claude/plugins/ and follow it by reading, which works identically, and tell the person to reload so the next run is native. Following it from disk is the fallback; skipping it is not.
  • Its scripts live beside that file, which is where the <scroll-craft> paths below point.
  • Chromium for Playwright (npx playwright install chromium), for verification.

Read references/pipeline.md before the first conversion.

The quality argument

The invocation may name a level: fast, balanced or high, anywhere in the arguments (/splat-site my-clip.mp4 high, or "build a site from this clip, balanced"). Take it as given and use it for the whole run without asking again.

When no level is named, use fast. It is the only level that works on every host, it turns a clip into a scene in minutes rather than an hour, and it gets a real page in front of the person while there is still time to change the design. Say which level you used and what it costs them, in one line, so the choice is visible rather than silent:

Converting at fast, which takes a few minutes and is softer up close. Say the word and I will rerun it at high, which trains for 30 to 60 minutes and looks considerably better.

Upgrading later is cheap and nothing about the page depends on the level: reconvert into a new scene folder, rerun stage-init.mjs against it, and the same markup renders the better capture.

Step 1: One interview, not two

Gather everything in a single pass, then write it down. scroll-craft's own brief covers eight topics and explicitly reuses answers already supplied, so asking its questions here and handing it the file means the person is never interviewed twice.

Ask, in one message: what the video shows and what the place is; who the page is for and what they must believe by the end; the one action the visitor should take; the scroll journey in their own words, where it should feel calm and where intense, and the one moment they should remember; how far from premium-minimal they want to go; what photos, footage, logo or palette already exist; and whether anything about the capture is known to be awkward (low light, glass, a subject they walked backwards away from).

Write the answers verbatim into <workspace>/builds/<name>/BRIEF.md, in their words. If the person has delegated creative direction or is unreachable, author the brief and mark it as authored rather than interviewed. Everything downstream reads from that file.

Step 2: Reconstruct

splatsite convert <video> --out ./scene                       # fast by default
splatsite convert <video> --quality high --out ./scene        # add --image splatsite-recon:dev for a local build

Use the level the invocation named, or fast when it named none:

LevelTimeNeedsUse when
fast (default)1-3 min on GPU, 10-30 min on CPUanythingthe default: a real scene today, and the only level a CPU-only host can run
balanceda few minutesGPUa better feed-forward result without a full training run
high30-60 minGPUasked for, or the capture itself is the point of the site

Start a high run in the background and do Step 1's writing and Step 4's planning while it runs; every stage is resumable, so an interruption costs only the stage it was in. Two things to mention once rather than discovering later: fast and balanced route through a model whose licence excludes the EU, UK and South Korea, and a capture with spherical harmonics may come back as PLY tiers plus a sog-pending marker that splatsite finish <scene> completes on a GPU machine.

Step 3: Judge the capture before designing anything

node <skill>/scripts/scene-plan.mjs ./scene

It prints the tiers, the splat count, the named camera poses a page can fly between, and it exits 2 on anything that would produce a blank page. The failure worth knowing by name: when the footage was shot walking backwards, the derived walking direction faces away from the geometry, and the page loads millions of splats and renders nothing. The planner catches it and names the fix. Do not design around a capture you have not planned; a bad capture is a reshoot, not a styling problem, and the reshoot advice is in references/pipeline.md.

Look at the posters and a few frames under scene/stages/images/ too, and check that the capture is what the person said it was. Scene folders get reused, misnamed and handed over second-hand, and a page written from the brief rather than from the pixels will confidently describe a sports ground over footage of a market. If the capture and the request disagree, say so before building, write copy that describes what is actually there, and flag the mismatch at the top of the brief. Never paper over it with plausible copy.

The harness can tell you a capture rendered; only you can tell whether it is worth building a site around.

Step 4: Choose the route

The template route. The CLI already ships a finished photo-walk page: the capture as a fixed world, pins holding photos at the spots they were taken, an album, a route map, an orbit viewer. If the ask is "my photos, in the place I took them", fill in the manifest's spots and build. Every manifest key is documented in <cli>/docs/manifest.md.

Each spot needs a position in the walk's own {t, a, h} coordinates. Do not estimate them, and do not assume frame numbers follow the walk: the extractor drops blurry frames and a phone's path is not monotonic, so "every third file" scatters the pins. Derive them from where the cameras actually stood:

node <skill>/scripts/frame-spots.mjs ./scene --count 5 --photos ./pics   # add --write to fill the manifest
splatsite build ./scene --photos ./pics --out ./site

frame-spots.mjs also copies the chosen frames into the photos folder, which is what to do when the person has no separate photographs and wants stills from the capture itself. It writes placeholder labels and captions on purpose: replace them with what the photo actually shows before building, because placeholder captions are not a page.

That is the whole job. Do not rebuild it by hand. That page is itself a scroll-craft build — it ships the same engine — so its copy, theme and structure still answer to scroll-craft's taste floor, and anything beyond filling in spots and theme colours means taking the bespoke route rather than hacking the template.

The bespoke route. When the page has to argue something, a property, a venue, a product, a brand, the capture is evidence and the page is the argument, so the structure has to be designed. Continue to Step 5.

Either way the page follows the waypoint walk, the grammar in references/house-pattern.md: one live place on one fixed stage, scroll walking the camera along an authored path, waypoints anchored as pins, a route map for nav, pin flight as the signature move, a rise for the peak, and arrival for the close. Read it before planning anything. Depart from it only when the brief genuinely demands something else, and then say which rule you broke and why.

Say which route you chose and why, in one sentence, before building.

Step 5: Build the bespoke page

Install the stage first, so the design work has real poses to score against:

node <skill>/scripts/stage-init.mjs ./scene --out ./build --stops 5

This puts the renderer, the capture tiers, the posters and a scene.json of named poses into the build, and prints the markup to paste. Full contract: references/stage-api.md.

Then invoke the scroll-craft skill for the page itself. This is the step that makes the result a page rather than a viewer with captions, and it is not optional: it carries the grammar, the feeling curve, the fingerprint gate and the taste floor this skill deliberately does not duplicate. Writing the markup yourself and calling it done is the one way to fail this skill while appearing to finish it. Tell it, in the invocation:

  • The brief is already written at <path>/BRIEF.md; do not re-interview.
  • The grammar is given, not chosen: the waypoint walk, specified at <skill>/references/house-pattern.md. Read it first. It fixes the structure, the nav, the hero, the signature move, the peak and the close, and it carries hard bans: no acts, no sections in document flow, nothing scrolling over the canvas, no wordmark bar, no orbit, no cuts. What is still scroll-craft's to decide is everything that makes this build its own: palette, type, voice, the feeling curve, the copy, and what the waypoints are.
  • The world is one fixed 3D capture behind the whole page. The camera is driven by the page's track; the device reference is at <skill>/references/stage-api.md.
  • The peak is the rise, the leg that lifts to see the whole place at once, because that is the move a visitor cannot make themselves. Give it the largest span and an authored silence in front of it.
  • Scrims must be siblings of the copy, never pseudo-elements, and position: absolute inside the act's own stage, never position: fixed across the page. Captures are noisier than photographs, so copy needs real protection.
  • The engine reads data-sc-kinetic from the element carrying data-sc-cue, so a split headline needs both attributes on the same tag.

The grammar is in references/house-pattern.md and the camera patterns, interaction ideas and traps are in references/page-recipes.md. Read both before scoring the page.

Theme with scroll-craft's tokens and pull the palette from the capture itself rather than inventing one; the scene's own ground colour is in the manifest's theme.

Step 6: Verify on the built page

For the template route, splatsite check is the whole verification: the page itself is already tested in the CLI's own suite, so what needs proving is that this capture renders in it. For the bespoke route both checkers matter, and they look at different things.

Run splatsite check in the background. Under software rendering a few million splats can take two to three minutes to load, sort and paint, which is longer than a default command timeout; killed mid-flight it reports an opaque closed-page error rather than a timeout.

splatsite check ./build --out check.png                       # does the world actually render?
node <skill>/scripts/stage-probe.mjs ./build --positions 10   # does the camera answer the scroll?
node <scroll-craft>/scripts/serve.mjs --root ./build --port 4500 &
node <scroll-craft>/scripts/shoot.mjs --url "http://localhost:4500/?ss-tier=software&ss-still=1" --out lab/shots
node <scroll-craft>/scripts/shoot.mjs --url "http://localhost:4500/?ss-tier=software&ss-still=1" --out lab/mobile --width 390 --height 844
node <scroll-craft>/scripts/shoot.mjs --url "http://localhost:4500/?ss-tier=software&ss-still=1" --out lab/reduced --reduced-motion

splatsite check loads the page under a software renderer and reports whether the stage went live, how many splats loaded, how much of the frame they covered and whether the console was clean. Coverage near zero with a nonzero count is the backwards-frame failure from Step 3, not a rendering bug.

For the waypoint walk, stage-probe.mjs is the verification, not a shortcut to it. scroll-craft's harness samples positions inside acts, and this grammar has none, so it photographs the first screen and stops: it reports no dead scroll because it never walked. Run the probe with --shots lab/probe instead, which screenshots every position and tiles a contact sheet, and read that sheet. Still run splatsite check for the render proof.

node <skill>/scripts/stage-probe.mjs ./build --positions 10 --shots lab/probe

stage-probe.mjs asks only the 3D question and answers it in seconds: it reads the camera signature the stage publishes at each scroll position and fails when too much of the page leaves the camera where it was. Run it before the screenshot harness, because it finds the same dead scroll far faster, and because on a busy or GPU-less host the full harness can lose its browser mid-walk. If that happens, the run is an environment fault, not a page fault: rerun it alone, and if the browser still dies, point it at <skill>/scripts/chrome-software.sh with SCROLLCRAFT_CHROME, which forces the same software-WebGL flags splatsite check uses.

Both query parameters matter. ?ss-still=1 stops the renderer whenever the camera has settled, which is the difference between a harness run that completes and one that dies on its first screenshot: a canvas that never stops drawing never gives the harness the quiet frame it waits for. ?ss-tier=software keeps the fetched capture small, since a headless browser walking a multi-million-splat scene can run out of room and close the page, which surfaces as an error that reads like a page fault and is not one.

The scroll-craft harness walks each act and reports dead scroll, cues that never peak and contrast measured on the composited page. The stage publishes its camera signature so a moving world is not read as a frozen one; an act that deliberately holds needs data-sc-verify-hold="true" from you.

If the screenshot harness cannot complete a run on this machine, say so plainly and do not pretend the page was verified at every position. splatsite check plus stage-probe.mjs still prove the world renders and answers the scroll; take a handful of screenshots yourself at chosen scroll positions to look at composition, and name the mobile and reduced-motion passes as not covered.

Then do the part neither covers: read the contact sheet, scroll the page cold and write one word per act for what you felt, and diff that against the feeling curve in the brief. Where they disagree the page is wrong, not the brief.

Step 7: Hand it over

Report: which route you built, the capture's quality level and splat count, coverage and the harness findings, where the scene folder and the build are, and the command to serve it. Then say what a green run does not cover, because for this format the gaps are real: a physical phone (headless Chrome cannot reproduce a phone's GPU memory limits with millions of splats), a real GPU's appearance versus SwiftShader, and whether the page means anything.

Working rules

  • Long conversions run in the background; never sit and wait on a 40-minute training run when there is brief and score work to do.
  • Never hand-edit a capture file. Edit the manifest, or reconvert.
  • Keep the scene folder and the build separate: stage-init.mjs copies what the page needs, and a rebuild should never be able to destroy the reconstruction that took an hour. When a scene belongs to someone else, copy it into your workspace before editing its manifest.
  • Only one headless browser run at a time on a software renderer; they starve each other.
  • Quote real times and real numbers from the run, not estimates, once you have them.

The pipeline

The reconstruction half

Everything here is about turning a video into a scene folder. Read it before running a conversion, and again when one goes wrong.

The CLI

splatsite ships inside this plugin at <plugin>/cli, and the scripts here find it there automatically. It may also be on PATH; otherwise run node <cli>/bin/splatsite.mjs. The resolution order is $SPLATSITE_CLI, the plugin's own cli/, a splatsite on PATH, then a splatsite/cli above the working directory. Say which one you used, because a user with two checkouts will otherwise wonder which image and template they got.

Reconstruction runs in Docker. The image is ghcr.io/shamlikt/splatsite-recon:latest by default, splatsite-recon:dev for a local build, or whatever SPLATSITE_IMAGE names. A host GPU is detected and used automatically.

Quality levels

LevelMethodTimeNeedsOutput
fastWorldMirror 2.0, feed-forward1-3 min on GPU, 10-30 min on CPUanythingno spherical harmonics, .sog directly
balancedWorldMirror 2.0, higher fidelitya few minutesGPUcarries SH bands
highCOLMAP poses + 30k-step gsplat training30-60 minGPUbest quality, carries SH bands

fast is the default, and --quality may be omitted. Pick high when the person asks for it or when the capture itself is the point of the site; a fast scene on screen today is worth more than a better one in an hour when the page's structure is still being decided, and the two are interchangeable afterwards. A high run on a CPU-only host is refused immediately rather than failing an hour in.

--scale N (20-100) reduces frame width and cuts time roughly with the square of the number. --frames N overrides the frame count. Every stage is resumable: rerun the identical command after an interruption and it skips what finished, using markers under <out>/stages/.

Licensing, said plainly

fast and balanced route through Tencent HY-World 2.0, whose community license excludes the European Union, the United Kingdom and South Korea from its territory. high uses only COLMAP and gsplat, which carry standard open-source terms and no territory carve-out. If the person is in one of those places, or the work is commercial and they have not read that license, recommend high and say why in one sentence.

The SOG finish step

A capture with spherical harmonics needs a GPU encoder to compress into .sog. A container often has no usable Vulkan adapter even on a GPU host, so the container writes capture*.ply plus an empty sog-pending marker and exits 0. That is deferral, not failure. splatsite convert then runs the finish step on the host automatically. If the scene still has a sog-pending marker afterwards, run splatsite finish <scene> on a machine with a GPU; a built page needs .sog, and splatsite build and this skill's stage-init.mjs both refuse while the marker is there.

Judging a capture before designing anything

Run node scripts/scene-plan.mjs <scene>. It exits 2 on anything that would produce a blank or broken page. Three findings matter most.

The frame points away from the capture. The walking direction is derived from where the phone moved, not where it looked. Footage shot walking backwards, keeping a subject in frame, produces poses facing empty space: the page reports itself live with millions of splats loaded and renders nothing. The fix is to negate frame.fwd and frame.right in the scene's manifest.json and rerun the planner. If a page ever comes back live: true, count > 0, coverage: 0, this is the first thing to check.

The walk is short relative to the capture. A capture whose path is a small fraction of its radius does not reward flying along it; build the page around orbits and held poses instead of a long travel.

Registration warnings on high. The poses stage reports how many frames COLMAP registered. Below 80% is a warning and below 50% is treated as failure, both meaning too little texture, too much motion blur, or too fast a sweep. Reshoot advice worth giving verbatim: walk slowly, keep the subject in frame, overlap each step heavily, avoid blank walls and mirrors, and shoot a loop back to the start if the space allows it.

Failures you will actually hit

GPU memory guard refuses a stage. On a unified-memory host, another process holding GPU memory makes training thrash rather than fail. The stage refuses up front and names the other GPU users. Stop them and rerun the same command; it resumes.

high training dies in the first seconds with "No space left on device". The full message is RuntimeError: unable to allocate shared memory (shm) for file </torch_…>: No space left on device (28), and nothing is out of space: the device it names is /dev/shm, which Docker gives a container 64 MB of by default. The trainer's dataloader hands decoded frames back from its worker processes through shared memory, so a 1080p capture exhausts that within a few steps. convert now passes --shm-size 16g, so this should not recur; a checkout older than that fix needs --shm-size added to dockerArgs() in cli/lib/docker.mjs, or the same docker run issued by hand with the flag. Only high is affected — fast and balanced are feed-forward and use no dataloader workers, so a host where they both pass proves nothing about this. Frames and poses are kept, so a rerun resumes straight into training.

Root-owned scene files. The container runs as root, so the output may not be yours. convert detects this and prints the exact chown to run before building.

Chromium missing for check. npx playwright install chromium once. On a flaky network, download the build another way and put it under ~/.cache/ms-playwright/.

splatsite check appears to hang. It does not: under SwiftShader a multi-million-splat capture takes two to three minutes to load, sort and paint. Run it in the background and read the result when it lands. A run killed by a command timeout reports a closed page rather than a timeout, which reads like a page error and is not one.

A tier file is missing. The scene's manifest names three tiers. If one is absent the page falls back to the desktop tier on every device, which is a slow phone, not a broken page, but say so rather than letting it pass silently.

The stage

The splat stage: a capture as a scroll-craft device

assets/splat-stage.js mounts a Gaussian-splat capture as one fixed world behind the page and flies its camera from scroll-craft act progress. Acts stay ordinary scroll-craft acts; they just also say where the camera should be.

Install it

node <skill>/scripts/stage-init.mjs <scene-dir> --out <build-dir> [--stops 5]

Copies vendor/ (three.js + Spark) and splat.js from the splatsite CLI template, splat-stage.js and splat-stage.css from this skill, the capture tiers and posters into <build>/assets/, and writes <build>/scene.json. It only writes those files, so it is safe to rerun over a build in progress after a reconvert. It refuses on a scene whose frame faces away from the capture, or one still waiting on SOG encoding.

Wire the page

Order matters: the import map must precede the module, and the engine must be mounted.

<link rel="stylesheet" href="scrollcraft.css">
<link rel="stylesheet" href="splat-stage.css">
<script type="importmap">{"imports":{"three":"./vendor/three.module.js","three/addons/":"./vendor/three-addons/","@sparkjsdev/spark":"./vendor/spark.module.js"}}</script>
...
<div class="ss-stage" id="stage" data-ss-stage="scene.json" data-sc-verify-state="" data-ss-look="5 3">
  <img class="ss-poster" src="assets/desktop.jpg" alt="What the visitor is looking at.">
  <canvas class="ss-canvas"></canvas>
</div>
...
<script src="scrollcraft.js"></script>
<script>ScrollCraft.mount(document.body);</script>
<script type="module" src="splat-stage.js"></script>

Use the poster path stage-init.mjs printed: a scene converted with posters gives you its own JPEGs, and one converted without them gets a flat SVG placeholder instead, so the filename is not fixed. id="stage" is what splatsite check looks for; without it that checker reports the page is not a splat site at all. The stage element holds the poster and the canvas and nothing else: copy goes in the acts or in a fixed copy layer above it, never inside the stage.

Track mode: the waypoint walk

The grammar in house-pattern.md has no acts. Declare the walk as a track of legs instead, and the stage sizes the page, drives the camera and grades the copy from it.

<div data-ss-track hidden>
  <div data-ss-leg="gate>w3"   data-ss-w="1.3" data-ss-label="The gate"></div>
  <div data-ss-leg="w3>w2"     data-ss-w="1.2" data-ss-linger="0.3" data-ss-label="The long table"></div>
  <div data-ss-leg="w2>wide"   data-ss-w="2.4" data-ss-label="The rise"></div>
  <div data-ss-leg="wide>gate" data-ss-w="1.3" data-ss-linger="0.35" data-ss-label="The overlook"></div>
</div>
<div data-ss-spacer></div>

<div class="copy">
  <h1 data-ss-window="0 0.2 0 0.06">The place</h1>
</div>
AttributeMeaning
data-ss-trackholds the legs; it is metadata, so keep it out of the layout
data-ss-lega pose to hold, or a>b / a>b>c to fly across the leg
data-ss-wthe leg's weight in viewport heights (default 1.3)
data-ss-linger0 to 0.6, the last fraction of the leg spent standing at its end pose
data-ss-labelthe waypoint's name, carried on the ss:waypoint event
data-ss-fov, data-ss-orbit, data-ss-pushas in act mode, per leg
data-ss-spacerthe only element in document flow; the stage sets its height
data-ss-windowfrom to [rampIn rampOut] in whole-track progress, for copy in the fixed layer

The stage publishes --ss-leg, --ss-legp and --ss-u on the root element, mirrors the leg index into data-ss-leg on the stage, and fires ss:waypoint when the leg changes, which is what a route map listens to. The leg deliberately stays out of data-sc-verify-state: a signature that changes when the leg changes makes two identical camera positions look different and hides the very stillness the attribute exists to reveal. SplatStage.on("sample") hands the page a strided sample of the capture's splats, so the map can be a plan of the real place. A pin that has been flown to gets is-visited, so the map can record where the visitor has been.

The spacer is sized at mount and again on load and once fonts settle, because a viewport height read as zero at the wrong moment collapses the whole track to nothing with no error anywhere.

Act attributes

The acts that drive the camera are ordinary scroll-craft acts, and in practice they are data-sc-act="pin" sections: the world is already fixed, so the act's job is to hold its copy still while the camera travels. data-ss-move on an element that is not an act still works, falling back to the element's own geometry, but the engine then publishes no progress for it and spans and dwell stop applying. Write them as pin acts.

AttributeMeaning
data-ss-move="w2"hold the camera at pose w2 for this act
data-ss-move="gate>w3"fly from gate to w3 across the act's progress
data-ss-move="gate>w2>rise"fly through several poses, evenly across the act
data-ss-fov="60"field of view in degrees for this act
data-ss-orbit="16"degrees of yaw swept around the target across the act
data-ss-push="0.35"dolly the eye this fraction of the way toward the target
data-ss-ease="linear"constant rate instead of the default ease-in-out

Pose names come from scene-plan.mjs: gate, rise, close and wide from the capture itself, w1..wN spaced along the walk. An unknown name logs a warning naming the poses that do exist, and the act is ignored rather than silently freezing the camera.

The camera reads --sc-p from the active act, so spans, dwell and any future engine pacing change apply to the 3D camera automatically. When an act does not publish it, the stage falls back to the act's own geometry, so a plain section still works.

Pins

<button data-ss-pin='{"t":0.42,"a":0.1,"h":0.15}' data-ss-fly="w3">The bench</button>
<button data-ss-pin='[1.2,-0.4,0.8]'>A world point</button>

{t, a, h} is the walk coordinate system: t along the path from 0 to 1, a across it, h above the ground. Raw [x, y, z] works too. Do not guess these numbers — a guessed pin lands in the trees rather than on the thing you meant. Get real ones from scripts/frame-spots.mjs <scene>, which reads where each frame's camera stood and prints coordinates you can paste straight in. The stage projects each pin every frame, sets --ss-x, --ss-y and --ss-z on it and hides it when it is behind the camera or off frame. Clicking dispatches a bubbling ss:pin event carrying the world point, and with data-ss-fly it flies the camera to that pose until the visitor scrolls again.

Pins are the interaction this format is actually good at. A pin that opens a photo taken at that spot, a caption, or a detail panel gives the visitor a reason to stop, which a flythrough alone never does.

JavaScript

await SplatStage.ready;
SplatStage.pose("rise");                  // { eye, target }
SplatStage.resolve({ t: 0.5, a: 0, h: 0.2 });   // walk coordinates -> world
SplatStage.project([x, y, z]);            // world -> { x, y, z, visible } in CSS pixels
SplatStage.flyTo("w4", 2600);             // take the camera for 2.6s; scrolling returns it
SplatStage.on("paint", () => {});         // ready | paint | progress | pose

flyTo and project are what a signature move is built from: the page decides what to fly to and what to draw over the world, and the stage stays a mechanism.

What it handles so pages do not

The dead-scroll check. scroll-craft's harness reads data-sc-verify-state; a stage whose only change is inside a WebGL canvas looks frozen without it. The stage writes a rounded camera signature there every time the view changes. On an act that deliberately holds, add data-sc-verify-hold="true" yourself so an authored stillness is not read as a fault.

Reduced motion and machines with no WebGL2. Neither fetches the capture. The poster stays, pins are hidden, and ss-poster-only goes on the root element. Write the acts so they still read as a page in that state, because for those visitors that is the page.

A tier override for verification. Load any page with ?ss-tier=software (or mobile, or desktop) to pin which capture it fetches. Use it for every harness run: a headless browser's renderer string does not always admit it is software, and walking a multi-million-splat scene through a screenshot harness will kill the tab with an opaque "target page has been closed" error that looks like a page fault and is not one. splatsite check needs no override; it detects the software renderer itself.

Device tiers. Software renderers get the lite capture, phones the mobile one, everything else the full one, each with its own pixel-ratio cap. Rendering pauses when the stage scrolls out of view.

Camera smoothing. Exponential, frame-rate independent, so scroll jitter does not reach the picture and a 30Hz phone settles over the same wall-clock time as a 120Hz laptop.

Gotchas

  • A scrim must be position: absolute inside the act's own stage, never position: fixed. A fixed scrim covers the viewport for the entire scroll, so every act's scrim ends up stacked over every other act's copy, and z-index inside the acts will not save you. Measured on a real build: a hero headline rendered at 75 of 255 with three page-level fixed scrims over it and 240 of 255 once they were scoped to their own acts. Worse, the usual way of hunting this (asking the browser what element is at that point) reports the text, because a scrim carries pointer-events: none and is skipped by hit-testing. Screenshot and measure the pixels.
  • data-sc-kinetic is read off the cue element itself. A split headline inside a cued wrapper never splits; the engine reads the attribute from the element carrying data-sc-cue, so the cue and the split belong on the same tag.
  • Add ?ss-still=1 for any screenshot harness. The renderer then stops as soon as the camera settles and restarts the instant it moves, so the frame on screen is still the right one. Without it, scroll-craft's shoot.mjs fails on its first screenshot against its own 30-second timeout, every time; with it, a 31-position walk of a 2.94M-splat capture completes and reports normally.
  • Screenshots of a live capture are slow. Under software rendering, one screenshot of a page with a painting splat canvas took tens of seconds and often exceeded a 60-second timeout, which is why a full screenshot harness struggles here and stage-probe.mjs exists. splatsite check copes because it takes exactly one, with a generous timeout.
  • A scrim over the world must be a sibling of the copy, never a ::before on it. The contrast pass hides text to photograph the background, and a pseudo-element of that text disappears with it, so the measurement grades the raw capture and never moves however much you strengthen the scrim.
  • Captures are visually noisy in a way photographs are not. Copy needs a real scrim or a solid panel; thin light type directly over splats fails contrast at some scroll position even when it looks fine at the two you checked.
  • Do not put data-ss-move on more than one act at the same scroll position. The stage picks the act straddling the middle of the viewport, so overlapping acts fight.
  • The first pose in scene.json is where the camera starts before any act is active. Order poses so that is somewhere sensible, or open the page with an act at the top.

The waypoint walk

The waypoint walk: the pattern every splat site follows

This is the structure the reference build arrived at, and it is the default for sites built with this skill. It is a grammar, not a skin: it fixes what a section is, what the chrome is for, how the visitor knows where they are, and how the page ends. Palette, copy, type and feeling curve are still scroll-craft's to decide per brand.

Depart from it only when the brief actually demands something else, and when you do, say which rule you broke and why. "It felt nicer" is not a reason.

What it is

One live 3D place on one fixed stage. Scroll walks the camera along a single authored path. The waypoints are the things worth stopping at, anchored as pins at real positions in the capture. Copy lives in one fixed layer, windowed against the whole track. The only thing in document flow is a spacer.

The camera translates along a path. It never circles a subject, never cuts, and never leaves the capture.

The seven rules

  1. No acts, no sections in flow. The page is one track of legs between waypoints, not a stack of blocks. A block-built page has seams, and a world with seams is not a world.
  2. Nothing scrolls over the canvas. Copy arrives inside the frame, at waypoints, in the fixed layer. No section slides up over the world.
  3. The nav is a route map, not a bar: a plan of the place drawn from the capture itself, the path, a you-are-here dot with heading, and the pins as buttons that fly you there. The part already walked is drawn in the accent, so the map is also a record of where you have been. One quiet text link carries the single action.
  4. The hero is the place, already in view. The camera is moving from the first notch, the title sits over the world as real markup, pins glow at depth. No wordmark bar, no scroll cue, no title card.
  5. The signature move is pin flight. A pin is a real button anywhere on the page, including the far ones. Click it and the camera flies along the walk to it; on arrival the photo blooms out of the pin where it was taken; click again for full screen with previous and next. The map stamps it visited. The move and the peak are the same system, because the peak is where every pin lights at once.
  6. One leg is the rise, and it is the peak. It gets the largest span by a visible margin, the widest view of the capture, the one second-person line on the page, and an authored silence in front of it so it has something to rise from. Adjacent legs never share a feeling.
  7. The close is arrival. The camera settles at an overlook with every pin lit, the album is laid out in the fixed layer with one quiet colophon, and it holds. The page stops and stays complete rather than fading out.

Bans

No data-sc-act. No section in document flow. No video. No orbit or turntable. No hard cuts. No wordmark-plus-action bar. No full-frame scrim. Nothing that scrolls over the canvas. No second stage.

Free look at the stops, not free roaming

While the camera stands at a stop, the visitor can look around: drag, swipe sideways, or use the arrow keys. Bound it to roughly 32 degrees either side and a little up and down, because a phone capture is a forward wedge and wider angles show its edges. Scrolling on eases the view back to the authored frame over about a third of a second. Between stops a drag is a scroll, not a look. Show a one-line hint once per session at the first stop and drop it on the first look.

Full roaming is deliberately not offered: the capture has no good angles off its axis, and letting someone walk into the void is worse than not letting them walk at all.

The look

A dark ground, so the capture is the brightest thing on the screen. Bone type. One accent that belongs to the pins and the walked path and nothing else — not to headings, not to buttons in general. Grain at a few percent. Every photo carries the same caption schema, gallery-label style; the variety on the page comes from the camera and from what shares the screen with it, never from styling each photo differently.

Pacing

Five or six legs. The peak leg runs about twice the length of an ordinary one. A three-photo walk lands near nine viewport heights, and each added photo adds roughly one more. No leg holds a still frame, and the total never lands in the band a previous build already occupies.

What the harness needs from it

The stage publishes data-sc-verify-state carrying the camera, the current leg and the lit pins, so the authored silence before the peak reads as anticipation rather than dead scroll. Mark deliberate holds so a still camera is never mistaken for a broken one.

Designing the page

Designing the page around a capture

scroll-craft decides what the page is. This file says what changes when one of its device families is a real 3D capture, and what a splat scene is actually good for.

The composition is a fixed world, not a stage per act

A scroll-craft page usually gives each act its own stage. A capture is one continuous place, so it lives in a single fixed element behind the whole page and the acts become copy over it that also move the camera. That is the same shape as worldflight, without the seam problem: there are no clips to cross-fade, because the world is geometry and the camera simply moves.

What this changes in practice: the copy layer needs its own scrims, the acts hold copy rather than imagery, and the page's ending has to resolve the camera somewhere deliberate rather than just running out of sections.

The capture counts as one device family

scroll-craft requires at least four families and forbids the same one twice in a row. A camera move is one family however many acts it spans. A page that is nothing but the capture moving is the failure the skill exists to prevent: five sections that behave identically are one section shown five times.

So plan at least three non-splat acts. The ones that sit well against a 3D world:

  • flow / reveal for the section that reads like a document, which every page needs once.
  • kinetic type for the line that has to land, placed where the camera holds still.
  • pan for a lateral rail of photographs taken at the places the camera has just walked past.
  • count only if the brand has real verified numbers.
  • pointer devices for the closing act, where the page stops moving and starts responding.

Two consecutive splat acts is the practical limit before something else has to happen.

Act patterns that work

Entrance. data-ss-move="gate>w2" over a held headline. The camera moving under the reader's own hand is the strongest open this format has, and it is the one thing a photograph cannot do.

Stand and turn. data-ss-move="w3" data-ss-orbit="16". The frame holds its position and sweeps, so copy can be read while the world still moves. This is where kinetic type belongs.

Lift. data-ss-move="w4>rise" data-ss-fov="60". Rising to see the whole place at once is the move a visitor cannot make themselves, so it is usually the peak. Give it the largest span on the page and make the act before it quieter.

Two warnings, both learned by shipping one. Aim the lift at the capture's centre, which is what the derived wide pose does, rather than along the walk: a camera that rises while still looking down the path frames bare ground, and a peak made of dirt is not a peak. And check what is actually up there. A phone carried at head height records no aerial detail, so lifting over a tree-covered site reveals canopy rather than the gathering underneath. When the capture has nothing above it, make the peak a lateral move or a close approach instead, and say so rather than spending the page's biggest act on a view the footage never contained.

Approach. data-ss-move="w2" data-ss-push="0.4" walks in toward one thing. Pair it with a pin on that thing.

Resolve. data-ss-move="close" or back to gate. Returning to where the page started reads as an ending; stopping mid-walk reads as the page having been cut off.

Interaction, which is the actual reason to use 3D

A flythrough is a video with extra steps. What a capture gives you that a video cannot:

  1. Pins on real places. A photo, a caption, a price, a name, anchored to the spot it belongs to and occluded correctly as the camera moves. Clicking one can fly there. Get the coordinates from scripts/frame-spots.mjs, which reads where each frame's camera stood and prints {t, a, h} you can paste straight into data-ss-pin; guessing them puts pins in walls.
  2. A waypoint rail. List the stops as buttons; SplatStage.flyTo takes the camera and the next scroll gives it back. This is navigation the visitor controls, which pinned scroll alone never is.
  3. Pointer lean. data-ss-look="5 3" on the stage gives a few degrees of parallax to the whole world. Small numbers. It should read as depth, not as a joystick.
  4. A signature move built from project(). Drawing the page's own graphics over world points, a measurement line, a route trace, a label that sticks to a doorway, is bespoke to this site and costs a few lines, because the projection is already there.

Pick one of these as the site's signature move and build it properly rather than sprinkling all four.

Mobile and reduced motion

Phones get the mobile tier and a wider field of view automatically, but composition is still art-directed separately: a pose framed for a wide desktop viewport crops badly in portrait, so check each act at phone size and move the pose, not just the type.

Under reduced motion and on machines with no WebGL2 the capture is never fetched and the poster is the page. Every act has to still say something in that state. Write the copy first and check it reads with the world removed.

When the template route is the better answer

The splatsite CLI already ships a finished photo-walk page: a fixed capture, pins holding photos grouped by spot, an album, a route map, and a full-capture orbit viewer. If what the person wants is "my photos, in the place I took them", build that with splatsite build <scene> --photos DIR --out site, hand-editing the manifest's spots. It is one command, it is already verified, and a bespoke page would spend a day arriving at the same thing.

Choose the bespoke scroll-craft route when the site has to argue something: a brand, a property, a product, a place being sold rather than remembered. Then the capture is the evidence and the page is the argument, and the structure has to be designed.

The manifest

The scene manifest

manifest.json is the one file that turns a raw capture (cameras + a Gaussian-splat file) into a photo-walk website. splatsite convert writes a starter one — reconstructed frame, ground plane and camera poses, spots: [] — into the scene folder; you edit it to add the pins and photos, then splatsite build reads it. This document lists every key, the coordinate system spots and poses are written in, and a worked example. A real, complete generated starter manifest (no spots edited in yet) is checked in at splatsite/examples/manifest.sample.json for reference.

The {t, a, h} coordinate system

A capture has one walking direction — the path the phone followed. Rather than writing every pin and camera position as raw [x, y, z] world coordinates (which depend on an arbitrary reconstruction origin and scale), most positions in the manifest can instead be written as an object { t, a, h }:

  • t — how far along the walk, 0 to 1. t: 0 is the near end of the captured path (frame.fwd0), t: 1 is the far end (frame.fwd1). Values are allowed slightly outside 0..1 to stand a little before the start or past the end.
  • a — across the walk, in the same units as the capture (typically meters). 0 is centered on the path; positive is to the right of the walking direction, negative to the left.
  • h — height above the ground plane. 0 sits on the ground (ground.point), positive is up.

Picture the walk as a straight lane on the ground: t is how far down the lane you are, a is how far you've stepped sideways off its centerline, and h is how far you've climbed above the floor. Under the hood (lib/manifest.mjs, resolve()), this is converted to a world-space point using the scene's frame:

world = frame.origin
      + frame.fwd   * lerp(frame.fwd0, frame.fwd1, t)
      + frame.right * a
      + frame.up    * h                          (measured from the ground plane)

Anywhere a {t, a, h} position is accepted, a raw [x, y, z] world-space array is also accepted instead — splatsite convert writes the three built-in poses (gate, rise, close) as raw arrays (derived directly from the reconstructed camera trajectory), while spot pins are usually easier to place with {t, a, h} since you're thinking in terms of "partway down the walk, a bit to the side, about knee height."

frame

The frame is the coordinate system every {t, a, h} position is resolved against. splatsite convert derives it from the reconstructed camera trajectory, so you normally don't hand-edit it, but it's worth understanding:

KeyTypeMeaning
up[x, y, z]The ground normal (points away from the floor). Need not be [0, 1, 0] — it's whatever the reconstruction's "up" turned out to be.
fwd[x, y, z]The walking direction — the direction t increases along.
right[x, y, z]Optional; the sideways direction a increases along. If omitted, computed as up × fwd.
origin[x, y, z]The world point where t = 0, a = 0, h = 0 (on the fwd0 end of the path, before the ground-plane height offset).
fwd0, fwd1numberThe range of "distance along fwd from origin" that t: 0 and t: 1 map to. Usually fwd0 = 0 and fwd1 = the length of the reconstructed path.

poses

Three named camera poses, each { eye, target } (both accept {t, a, h} or raw [x, y, z]):

  • gate — the opening view: where the walk starts, looking down the captured path.
  • rise — the overview: the camera lifts up to show the whole ground at once (this is also where the standalone orbit viewer starts from).
  • close — the closing view at the end of the walk.

spots

Each entry is one pin on the ground with one or more photos taken standing at that pin:

KeyTypeRequiredMeaning
labelstringyesThe spot's name (shown as a pin tooltip, and as the spot heading for multi-photo spots).
pin{t, a, h} or [x, y, z]yesWhere the pin sits on the ground.
eye{t, a, h} or [x, y, z]noWhere the camera stands to look at this pin. If omitted, it's computed automatically: back along the capture axis from the pin by config.axis.back, then in from there by config.standBack, at config.eyeHeight above the ground — i.e. leave it out unless the automatic stand-and-look position needs overriding (an obstruction, an odd angle).

Each photo is { file, title, alt }:

  • file — filename (not a path) of the photo, resolved against the --photos directory passed to splatsite build; it must exist there (splatsite build refuses with a clear error naming the missing file otherwise).
  • title — caption shown under the thumbnail (and, for a single-photo spot, next to the pin label).
  • alt — alt text for the image. Optional; falls back to title if omitted.

w/h (pixel dimensions) are written automatically by splatsite build after it resizes the photo — don't set them by hand.

Single vs. multi-photo spots

A spot with exactly one photo renders differently from one with several:

  • Single-photo spot: the album entry shows just that one photo, captioned with its title and the spot's label together (<title> <spot label>) — there's no separate spot heading, since the photo is the spot.
  • Multi-photo spot: the album entry shows a spot heading (the label, linking to the first photo) with a photo count, then each photo captioned with just its own title underneath.

Use a multi-photo spot when several photos were taken standing in roughly the same place (e.g. looking different directions, or a detail shot next to a wide shot); use separate single-photo spots when each photo belongs at a different point along the walk.

The three built-in poses are shown here as raw [x, y, z] world-space arrays, exactly as splatsite convert's starter manifest emits them — {t, a, h} objects are accepted too (and are often easier to hand-edit, since you're thinking in terms of "partway down the walk" rather than raw coordinates); see the note below for why this particular capture's poses were hand-edited.

Note on this particular capture: splatsite convert's starter manifest for this clip initially wrote frame.fwd/frame.right and the three poses pointing away from the reconstructed content, not into it — the phone was walking backwards (away from the subject, keeping it in frame) rather than forwards, and the auto-derived frame followed the direction the camera physically moved rather than the direction it looked. That produced a page that reported itself "live" with splats loaded, but rendered nothing (splatsite check returned coverage: 0). The fix, shown above: negate frame.fwd and frame.right (up and origin are unaffected — only the walking-direction axis was backwards), and recompute poses.gate / poses.rise / poses.close against the corrected frame — easiest by thinking in {t, a, h} terms first, then writing out the raw [x, y, z] arrays shown above, rather than trying to hand-fix the old raw arrays in place. If your own splatsite check comes back with live: true and a nonzero count but coverage: 0 (a "loaded but invisible" scene), suspect exactly this — check whether frame.fwd, from frame.origin, points toward or away from bounds.json's center (in the scene folder) before assuming something else is wrong.
